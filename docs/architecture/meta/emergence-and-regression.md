# 涌现与可回归验证：不冲突的工程化做法

你担心“涌现叙事”和“可回归验证”天然相悖：涌现意味着宏观不可预测，而回归测试意味着把期望写死。这个矛盾可以化解，但需要把“要验证什么”拆成不同层级，并把“新现象”当成可观测的变化，而不是必须阻止的偏差。

本文给出一个工程化框架：既允许系统产生新现象，又能在迭代中持续发现漂移、定位机制问题，并量化“涌现表现”的趋势。

## 1. 关键澄清：不可预测 ≠ 不可复现

- **涌现不可预测**：你无法在设计时枚举将出现哪些宏观模式。
- **但它仍可能可复现**：在同一版本、同一世界、同一脚本/seed 下，宏观模式可以稳定重现（或至少在统计意义上稳定）。

因此，“可回归验证”不等于“冻结宏观剧情”。它更像：
- **验证底层机制不崩**（不变量、守恒、合法状态、边界条件）
- **监控宏观签名的漂移**（分布/趋势变化是否超出可接受区间）
- **将“新现象”显式标注为版本差异**（可解释、可比较、可复盘）

## 2. 两层回归：微观硬断言 + 宏观软对比

### 2.1 微观（硬断言，门禁）
目标：确保你改机制时不把系统基本规律打碎。

典型断言（示例）：
- 世界结构合法：Map/Scene/Interaction/Portal 引用闭合、可达性规则满足约束。
- 状态不变量：库存不为负、容量不超上限、位置/速度/目标一致性、事件执行顺序合法。
- 机制闭环可达：Need→Planner→Action→Need 恢复在有限步内发生。

这类测试不关心“剧情长啥样”，只关心“机制有没有坏”。

### 2.2 宏观（软对比，告警/留档）
目标：允许涌现变化，但要能**量化变化**并把变化变成可讨论的证据。

做法：把一次运行抽象为一个 **行为签名（Behavior Signature）**：
- **标量指标**：均值/分位数/比率（例如平均旅行成本、缺货率、危急需求占比）
- **分布指标**：行动类型分布、目标交互点分布、库存分布
- **时间序列**：按窗口聚合的趋势（例如每 1k steps 统计一次）

回归不判断“对/错”，而是输出：
- 相对基线的差异（delta）
- 差异是否超过阈值（soft warning）
- 差异出现在哪些窗口/哪些实体/哪些资源上（定位线索）

## 3. “涌现性能”如何量化：三种强度，从易到难

你关心的“涌现性能”建议拆成两轴：
- **新颖性（Novelty）**：系统是否产出更多不同的行为/事件组合
- **结构性（Structure）**：这些变化是否是有因果结构的模式，而不是纯噪声

我建议按实施成本分三档推进（你可以随时拍板选其中一档作为近期 KPI）：

### 档位 S0：生存/供给/效率（最低成本，强相关）
用于保证系统能长期运行且行为不塌缩：
- Need 危急比例（critical rate）
- 资源缺货/失败尝试比例（stockout / failureReason 统计）
- 平均旅行成本、平均停滞时长（movement + planner）
- 资源吞吐（consumed/produced/decayed）

优点：直接从 Telemetry 得到，稳定可靠。

### 档位 S1：行为多样性（中成本，最实用的“涌现”代理）
把“系统是否只会做一件事”量化出来：
- 行动类型熵（Action entropy）
- Planner 目标多样性（target diversity）
- 交互点访问的长尾程度（Gini/Top-K 占比）
- Agent 间行为差异（个体多样性：每个 agent 的动作分布距离）

优点：能捕捉“机制越来越丰富/越来越塌缩”的趋势。

### 档位 S2：叙事结构与母题（高成本，但最贴近“涌现叙事”）
需要对事件流定义“叙事 token”（例如：出发→抵达→取水→失败→转向→协作…）：
- 母题（n-gram）覆盖率与新母题出现率
- 角色弧线：需求波动→目标选择→结果 的可重复模式数量
- 变点检测：出现新的稳定运行“状态机区域”（regime change）

优点：更接近你要的“故事涌现”，但需要先定义事件词表与抽象层。

## 4. 当“新现象”与既有测试冲突时怎么办

把测试分成两类即可避免相悖：
- **不变量测试**：不随“故事”变化而变化，应该长期稳定（门禁）。
- **签名/指标测试**：默认不门禁；当变化超过阈值时触发“需要解释”的报告，而不是失败。

当你有意引入新机制导致宏观行为变化：
- 更新基线（baseline）并在变更说明中写明“预期宏观变化点”
- 把变化解释绑定到指标：例如“行动熵上升 20%，缺货率下降 5%”
- 如果变化带来副作用（例如 travelCost 暴涨），优先从机制/参数回滚或加约束

## 5. 我对回归结果的固定汇报格式（你可只看摘要）

每次 core regression / soak 结果，我会给你一页摘要：
- **版本与配置**：commit、编译器、world/seed、steps/wall time
- **健康度**：崩溃/断言/critical need、失败尝试、库存异常
- **关键指标差异**：相对基线的 Top 变化（+/-）
- **初步结论**：属于预期改动 / 疑似漂移 / 明显退化
- **下一步建议**：二选一（例如“调参”或“改机制/加约束”）

---

建议默认先落地 S0+S1（低成本但信息量足），S2 作为“叙事 token/母题”系统成型后再加。
